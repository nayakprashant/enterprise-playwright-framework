# Task: Automate Test Cases Using Enhanced Codegen Steps and Existing Playwright Framework

You are working in an existing Playwright automation framework built with TypeScript.
Your task is to create an automated test script using the provided test case Excel file and enhanced codegen recorded steps. You must reuse the existing framework and follow its architecture, coding conventions, and helper functions. Do not create a new framework or unnecessarily modify existing code.

## 1. Input Format

You will be provided with two inputs:

### 1.1 Excel File (Test Case Steps)
An Excel file containing the manual test case with:
- Step numbers
- Descriptions
- Expected results
- Locator information (if available)

### 1.2 Enhanced Codegen Steps
Playwright codegen recorded steps that have been enhanced with comments. Each codegen line is preceded by a two-line comment:

```
// Page: [PageName]
// Action: [Action being performed] on [Entity]
await page.locator('selector').click();
```

**Comment Structure:**
- **Line 1**: `// Page: [PageName]` - The name of the page where the action is performed
- **Line 2**: `// Action: [Action being performed] on [Entity]` - Description of the action and the target entity

**Example:**
```
// Page: LoginPage
// Action: Click on My Account link
await page.locator('//*[@id="primary-menu"]/ul/li[3]/a').click();

// Page: LoginPage
// Action: Enter username into username field
await page.locator('#username').fill('customer');

// Page: LoginPage
// Action: Enter password into password field
await page.locator('#password').fill('password123');

// Page: LoginPage
// Action: Click on Login button
await page.locator('//*[@id="post-10"]/div/div/form/p[3]/button').click();
```

## 2. First, Inspect the Existing Framework

Before writing any code:

- Inspect the project structure and identify the existing test files, configuration, helper functions, test data handling, and framework utilities.
- Review the existing test scripts to understand how tests are structured and executed.
- **Identify all existing page objects** in the `pages/` folder.
- For each existing page object, note the locators that are already defined.
- Identify the appropriate location for the new test.
- Determine whether the framework already provides wrapper functions, custom assertions, test fixtures, hooks, or other reusable utilities.
- Reuse the existing implementation wherever appropriate instead of duplicating functionality.
- Do not modify the framework configuration or existing files unless required for this test.

## 3. Page Object Management Strategy

You must intelligently manage page objects based on the enhanced codegen steps:

### 3.1 Check for Existing Page Objects

For each unique page name mentioned in the codegen comments:
1. Check if a page object file already exists in the `pages/` folder with a matching name (case-insensitive).
   - Example: If comment says `// Page: LoginPage`, check for `LoginPage.ts`, `loginPage.ts`, etc.
2. If the page object exists, **reuse it**.

### 3.2 Handle Existing Page Objects

If a page object already exists:
1. Check if the required locators are already defined in that page object.
2. If a locator exists, **use the existing locator** from the page object.
3. If a locator does NOT exist:
   - Add the new locator to the existing page object class.
   - Follow the existing page object pattern (readonly properties, constructor initialization).
   - Use the selector from the codegen step.

### 3.3 Create New Page Objects

If a page object does NOT exist:
1. Create a new page object file in the `pages/` folder.
2. Name the file appropriately based on the page name from the comment.
3. Follow the existing framework's page object pattern:
   - Use readonly properties for locators
   - Initialize locators in the constructor
   - Include a public getter for the page object
   - Use the exact selectors from the codegen steps
4. Add all locators needed for that page based on the codegen steps.

## 4. Test Implementation Requirements

Create a complete Playwright test script that:

- Follows the existing framework's structure and coding conventions.
- Uses the existing test runner, configuration, fixtures, hooks, and helper functions where applicable.
- **Imports and uses the appropriate page objects** (existing or newly created).
- **Accesses locators as `objectName.memberName`** from page objects.
- Uses helper functions from `genericHelper.ts` for interactions (click, fill, getText, isVisible, etc.).
- Implements the test steps from the Excel file using the enhanced codegen information.
- Uses appropriate Playwright assertions with meaningful failure messages where supported by the existing framework.
- Uses appropriate waiting and synchronization mechanisms. Avoid unnecessary fixed delays such as `waitForTimeout()`.
- Keeps the test readable, maintainable, and easy to understand.
- Adds test hooks (beforeAll, afterAll, beforeEach, afterEach) with console.log statements if the framework pattern requires it.
- Do not add unnecessary abstractions, dependencies, or helper functions if the existing framework does not require them.

## 5. Locator Usage Requirements

- Use the exact selectors from the enhanced codegen steps.
- Do not replace them with alternative locators, text-based locators, role-based locators, or newly discovered selectors.
- Do not use AI to invent, modify, or optimize the supplied locators.
- Store locators in page objects following the framework's conventions.
- If a supplied locator does not work, report the failure and the affected step. Do not silently substitute another locator.

## 6. Test Data and Credentials
